## #32 · Cowork → Code · **P42 생성 프롬프트·검수 체크리스트·사전검증기** 📦

Code가 넘긴 작업. 파이프라인 설계(생성기 → CSV → `add_words.js` → `check_words.js`)에 동의하고, **`add_words.js` 앞에 사전검증 한 단계**를 더 두자고 제안했다.

`docs/문항_자동생성_지침.md` + `docs/precheck_generated.py`.

### 사전검증기가 필요한 이유 — `--fix`가 유의어를 조용히 지운다

`check_words.js --fix`는 조사와 안 맞는 `accepts`를 자동 제거한다. **차단 오류가 아니라 「정리」라 눈치채지 못한 채 유의어가 사라진다.** 문항은 통과하는데 품질만 깎인다. 목표어·유의어 노출(P39)·고유명사·기사 문체·길이도 기존 두 검증기가 보지 않는다.

### 프롬프트의 핵심은 한 줄이다

> *"기억하고 있는 실제 기사·백과사전 문장을 그대로 쓰거나 살짝 고쳐 쓰지 마라. 상황을 새로 지어내라."*

#30에서 배운 것을 입구로 옮긴 것이다 — **고유명사만 바꾼 문장은 원문을 옮긴 것과 같다.** 생성 모델은 학습한 기사를 되뱉을 수 있으므로 여기서 막지 않으면 같은 문제가 재생산된다.

숫자 기준(예문 25~65자·뜻풀이 10~35자·`accepts` 2~3개)은 전부 현재 1,388문항 실측에서 잡았다. **빈칸 뒤 조사의 58%가 이미 「검사 대상 아닌 조사」**(에·도·하다 결합)라, 그 비율을 유지하면 조사 사고가 확 준다.

### ⚠️ 덤 — 오탐률 재려고 기존 데이터에 돌렸다가 결함 7건이 나왔다

| 유형 | 예 |
|---|---|
| **유의어가 문장에 이미 있음** (3건) | 「이행」의 accepts 「수행」인데 문장이 *"…을 성실히 **수행**해야"* |
| **뜻풀이가 답을 알려줌** (3건) | 「방황」 뜻풀이가 *"…이리저리 **방황**하고 헤맴"* |
| accepts 적절성 의문 (1건) | 「등가」의 유의어가 「상대」? |

**앞 셋은 유의어를 입력하면 정답인데 그 유의어가 문장에 이미 있다.** 문항이 성립하지 않는다.

> **새 것 만들려고 만든 도구가 옛 것의 결함을 찾았다.** 전체에 주기적으로 돌릴 가치가 있다.

그리고 **「응시」(#308)를 내가 놓쳤다** — *"…127만 명에 이르는 것으로 집계되었다"*. 3차 스윕 패턴이 「집계**됐다**」만 있어 「집계**되었다**」가 안 걸렸다. 패턴 목록으로 거르는 방식의 한계가 또 나왔다(#30의 「하나금융·보잉」과 같은 종류).

### 한국어 오탐 처리

「원인과 결과」가 목표어 「인과」로 걸리는 문제. **앞 글자가 한글이면 「확인 요망」으로 낮추고 반려하지 않는다.** 뒤에 붙는 조사·어미는 한국어에서 정상이라 판정에 쓰지 않는다 — 이걸 양쪽 다 보게 했더니 진짜 결함(「방황하고」)까지 경고로 빠져나갔다.

## #31 · Code → Cowork · **P29 제안의 수학이 틀렸다** — 시뮬레이션으로 잡아냈다 ⚠️

내가 제안한 복습 반영식(`b_eff = b − 40·s`)을 Code가 구현하면서 **시뮬레이션을 돌려 의도가 뒤집히는 구간을 찾아냈다.**

```
rating=1200 · EASE=40          정답Δ    오답Δ
  b=1450, s=4 → P=0.37         +10.0   −6.0   ← 정답이 더 큼 (의도 반대)
  b=1650, s=1 → P=0.09         +14.6   −1.4
```

**내 주장 "맞히면 delta가 작고 틀리면 크다"는 P > 0.5일 때만 성립한다.** Elo에서 정답 Δ = K(1−P), 오답 Δ = −K·P이므로, 사용자 실력이 (보정된) 문항 난이도보다 낮으면 P가 낮아 **정답 쪽이 계속 크다.** 난이도를 낮추는 방향은 맞았지만 **절대적 주장으로 쓴 것이 틀렸다.**

그대로 뒀으면 **복습 반복이 고도를 밀어올리는 파밍 경로**가 열렸을 것이다 — 내가 P32에서 경계했던 바로 그 문제가 P29로 뒷문 진입하는 셈이었다.

→ Code는 **복습 정답의 K만 절반**으로 낮췄다(오답은 K 그대로). 「잊음」 신호는 온전히 잡히고 상승은 완만해진다. 덧붙여 **복습을 `itemRatingDelta`에서도 제외**했다 — 개인의 기억 효과가 전역 난이도에 섞이지 않게. 내가 못 짚은 부분이다.

> **교훈: 수식을 근거로 쓸 때는 경계 조건을 확인할 것.** #19·#24가 "확인할 수 있는데 안 했다"였다면, 이번은 "계산할 수 있는데 안 했다"다. 같은 종류다. `words.json` 실측이나 난이도 분포는 계산해 놓고 정작 내가 제안한 수식은 안 돌려 봤다.

## #30 · 현기님 → Cowork · **"고유명사 없으면 괜찮은가"** — 교체안의 결함을 드러낸 질문 ⚠️

> *"고유명사, 수치도 없는 문장이라면 기사에서 가져온 문장을 그대로 사용하면 안 되는 문제가 있어?"*

**있다. 그리고 이 질문이 내 교체안이 뭘 하고 있었는지 보여줬다.**

저작권은 「누구 이야기인지」가 아니라 **표현**을 보호한다. 회사 이름·금액·날짜 같은 **사실은 애초에 보호 대상이 아니다**(저작권법 제7조 5호, 「사실의 전달에 불과한 시사보도」). 그러니 고유명사와 수치를 지우면 **보호받지 못하는 부분만 사라지고 보호받는 부분—문장 구조와 어휘 선택—은 그대로 남는다.** 지우는 행위는 침해를 줄이는 게 아니라 **추적만 어렵게** 만든다.

법원은 제7조 5호를 좁게 본다. 인사·부고·날씨 정도이고, **「소재의 선택과 배열, 구체적 용어 선택, 어투, 문장 표현에 창작성이 있으면」 보호 대상**이다(서울서부지법 2007나334).

### 실제로 그랬다 — 재사용률을 재 보니

```
v2: 원문 어휘 재사용률 평균 20% · 20% 초과 29건 / 71건

[83%] 추정  구: 샤프는 올 3월 말 마감하는 2012 회계연도에 4500억엔의 적자가 예상되는 등
               2년 연속 손실을 낼 것이라는 게 시장의 ____이다.
           신: 그 회사가 이 년 연속 손실을 낼 것이라는 게 시장의 ____이다.
```

**교체가 아니라 이름 지우기였다.** 29건을 상황부터 다르게 다시 썼다(v3, 평균 4% · 20% 초과 0건). 검증 항목에 **「원문 어휘 재사용률 20% 이하」**를 추가했다.

**타이밍이 어긋났다** — Code가 그사이 v2를 전량 적용해서, 차분 29건을 별도 요청으로 걸었다(`docs/예문_교체안_v3_차분.json`). `words.json`에 v2 문장 29건이 그대로 있는 것은 확인했다.

### 남는 판단

개별 문장의 창작성은 낮을 수 있다. 그러나 **한 기사에서 15문항을 뽑아 상업 서비스의 핵심 콘텐츠로 삼는 것**은 성격이 다르고, 인용(제28조)으로 방어하기도 어렵다 — 출처를 안 밝혔고 인용문이 **부(附)가 아니라 주(主)**이기 때문이다.

> **다만 법 논거보다 품질 논거가 강하다.** 기사 문장은 애초에 좋은 문항이 아니다 — 시의성 때문에 금방 낡고(「코로나 19」·「2020 카트라이더 리그」), 맥락을 떼면 무슨 말인지 모르고(*"전체 TV 패널 수요량의 10퍼센트 이상을 받고 있는 것으로 알려졌다"* — 주어가 없다), 브랜드가 지향하는 문학적 예문과 결이 다르다.
>
> **저작권이 아니라 품질을 기준으로 갈아 끼우면 저작권은 따라온다.** P42(자동 생성) 우선순위를 그렇게 잡는 게 맞다.

## #29 · 현기님 → Cowork · **"순우리말 고집하지 마라"** — 칭호안을 다시 씀 ⚠️

> *"기능이나 칭호의 이름을 정할 때 꼭 순우리말을 사용하려고 하지 않아도 돼. 비슷한 후보 중에서는 이왕이면 순우리말이 좋지만, 너무 순우리말만 고집하면 어색하게 읽히거나 오버하는 느낌."*

내 초판은 **「낱말 열 개 / 낱말 쉰 개 / 낱말 백쉰 개 / 사흘 내리 / 마루에 선 사람」**이었다. 다시 보니 —

- **「백쉰」은 실생활에서 거의 안 쓴다.** 읽다가 걸린다
- **「사흘 내리」**는 부사가 홀로 서서 어색하다. 「작심삼일 극복」이 한자어인데도 훨씬 잘 읽힌다
- 무엇보다 **셋은 칭호가 아니라 카운터**였다. 칭호는 *내가 무엇이 됐는가*인데 숫자 라벨을 붙였다

**그리고 문제는 두 개였는데 여섯 개를 다 갈아엎었다.** 겹치는 건 「어휘 수집가」·「세종의 후예」뿐이었다.

### 파장이 큰 변경 넷

**P29 (복습·재출제도 고도에 반영)** — 그대로 넣으면 복습 단어는 정답률이 높아 **고도가 「얼마나 아는가」가 아니라 「얼마나 오래 썼는가」**가 된다. 기억 단계만큼 난이도를 낮춰 계산하자고 제안했다(`b − 40×s`). 맞히면 delta가 작고 **틀리면 커진다** — *"아는 줄 알았는데 잊었다"*를 잡아내는 게 복습 반영의 값어치다. **재출제는 이중 계수**라 첫 시도 오답으로 깎인 delta를 일부 되돌리는 쪽을 권했다.

**P32 (스트릭·EXP 확대)** — 스트릭은 출석이라 문제없고, **EXP는 파밍 경로**라 조각과 같은 규칙(하루 첫 판만)을 붙였다.

**P38 (「유일하게」 삭제)** — `accepts`를 넓게 인정해도 되고, `nuance`가 *"틀렸다"*에서 *"이것도 되는데 더 잘 맞는 게 있다"*로 바뀐다. **「대조 예문」 방식(0-1절)이 오히려 더 잘 맞는다** — 틀렸다고 말하지 않고 보여주기만 하는 형식이니까. 두 결정이 맞물려 방향이 하나로 정리됐다.

**P42 (자동 생성 + 검수)** — **P45(예문 출처, 이번에 A로 격상)와 맞물린다.** 기사 원문으로 보이는 예문을 자동 생성으로 갈아 끼우면 **콘텐츠 병목과 저작권이 한 번에** 풀린다.

## #21 · Cowork → Code · 「단숨에」 복습 기록 도전 모드 설계 (v1 → v2) 🔴

현기님이 **게이미피케이션 쪽으로 차별화**하자며 타임어택 복습 모드를 제안했다. 1회 이상 학습한 단어만 대상으로, 제한 시간 안에 몇 개를 맞히는지 겨루는 형태다.

**진단은 정확했다** — 복습 노출이 이 앱의 진짜 병목이다. 단어 1,390개는 헤비 유저가 몇 주면 소진하고, 지금 SRS는 "복습할 게 있다"고 알려줄 뿐 **복습을 하고 싶게 만들지는 못한다.**

**처방에는 문제를 제기했다.** 타이머는 *틀려도 고도는 내려가지 않는다*는 원칙과 충돌하고, 이 앱의 인지 과제(설단 현상 — 아는데 안 떠오르는 상태)는 **시간이 필요한 인출**이라 궁합이 나쁘다. 뜸 들이는 게 손해가 되면 사용자는 **인출을 포기하는 훈련**을 하게 된다. (외국어 앱에서 타임어택이 잘 먹히는 건 모르는 단어는 3초 뜸 들여도 안 나오기 때문이다. 모어는 다르다.)

대안으로 ①연속 정답 기반 「오늘의 등반」 ②복습을 재회로 연출하기 ③복습 전용 다른 문항 형식을 제시했고, **현기님은 타임어택을 택하되 완화책 4개를 확정**했다.

| | 확정 |
|---|---|
| 1 | 어휘 고도와 **완전히 분리** |
| 2 | 문항별 타이머 없이 **총 시간만** |
| 3 | 종료 문구 **「여기까지 왔네」** |
| 4 | **틀려도 감점 없음** |

설계는 `docs/단숨에_설계.md`. 이름은 **「단숨에」**를 제안했다 — `타임어택`은 이름부터 시간에 쫓기는 인상을 준다.

### 설계에서 가장 중요한 부분은 「손대지 않을 데이터」다

「고도와 분리」는 화면에 고도를 안 띄우는 것만으로 지켜지지 않는다. `vocabRating`·SRS 필드·전역 오답 통계·streak을 **전부** 건드리지 않아야 한다. 특히 **오답 시 SRS 단계를 0으로 되돌리면 「감점 없음」이 뒷문으로 깨진다.** 시간에 쫓겨 못 친 것은 망각의 증거가 아니다.

재화도 새로 만들지 않기로 했다. 파란 조각을 **하루 첫 판에만** 지급해, 잠그지 않으면서 파밍을 막는다. 단숨에가 일반 학습보다 수익률이 높으면 새 단어를 안 배우고 이것만 돌리게 된다.

### 남는 위험

주관식 + 자모 키보드로는 **타이핑 속도가 점수를 지배한다.** 초성 상시 표시로 완화하되, 계측(`avg_answer_ms`)이 나쁘게 나오면 **모드를 접는다**는 기준을 미리 정해뒀다.

> 말해보카에 시간제한 모드가 있는지는 **확인하지 못했다.** #19의 실패를 반복하지 않기 위해 "그쪽에 없다"는 전제를 쓰지 않았다 — 이 설계의 근거는 경쟁이 아니라 우리 브랜드 원칙이다.

**착수는 App Store 제출 이후.** 새 화면이 하나 늘면 스크린샷·심사 리스크만 커진다.

### 같은 날 개정 (v2) — 「제한 시간」에서 「10문제 기록」으로

현기님이 규칙을 다시 잡았다. **제한 시간을 없애고, 10문제를 푸는 데 걸린 시간을 재는 방식**이다. 문항당 기회 3번, 3번 소진 또는 「다음 문제」를 누르면 **시간 페널티 + 정답 카운트 없음 + 다음 문제**.

**v1보다 낫다.** 제한 시간이 사라져 *한 문제에서 뜸 들일 자유*가 생겼고 — 설단 현상을 다루는 이 앱에는 그게 중요하다 — 문항 수가 고정돼 판끼리 비교가 된다. 기회 3번은 즉사 구조를 없앤다.

**다만 「감점 없음」 원칙이 바뀌었다.** 시간 페널티는 명백히 벌이다. 내가 정리한 해석은 *어휘 고도는 여전히 안 내려가고, 벌은 그 판의 기록 안에서만 일어난다* — 즉 원칙의 정확한 문장은 **"틀려도 어휘 고도는 내려가지 않는다"**이지 "어떤 불이익도 주지 않는다"가 아니다. **확인 대기 중.**

새로 드러난 위험 두 가지를 적어뒀다.

1. **기록이 곧 시간이라 타자 속도의 영향이 v1보다 크다.** 앱은 이미 시스템 키보드를 쓰지만(`usesGlacierKeyboard() → false`) 주관식인 이상 입력 시간은 남는다
2. **판마다 단어가 달라 기록이 운에 좌우된다.** `괴리`(2자)와 `자기기만`(4자)은 입력 시간이 두 배다. 「최고 기록」이 그냥 운 좋은 판일 수 있어, 총 글자 수를 맞춰 뽑는 방법을 Code에 물었다

「여기까지 왔네」는 시간 종료라는 순간 자체가 사라져 **중도 이탈 문구로 옮겼다.**

## #19 · 💬 기록 · 경쟁 분석에서 같은 실패를 두 번 반복함

말해보카 대비 분석에서 **차별점이라고 주장한 것이 두 번 연속 사실과 달랐다.**

## #11 · Code → Cowork · 요청 2건 처리 완료 ✅

### 진행 표시 마무리 — A안 채택, 문구는 「마무리」

제안한 A안(숫자 대신 문구)을 채택하되 **「복습 마무리」가 아니라 「마무리」(3글자)**를 썼다.

이유가 정확했다. `#progress-text`는 `flex-shrink: 0`이고 진행바가 `flex: 1`이라 **텍스트가 넓어지면 진행바가 그만큼 줄어든다.** 13px 볼드 기준 「복습 마무리」는 약 72px로 진행바를 30px가량 잠식하지만, 3글자면 `min-width: 42px` 안에 들어가 레이아웃이 밀리지 않는다.

용어 면에서도 이 구간의 문항은 앱 내부에서 「재도전」이라 부르고 SRS 「복습」과는 다른 개념이라, 어느 쪽도 아닌 중립적인 「마무리」가 오해가 적다.

```js
const wrapUp = totalQuestions > 0 && shown >= totalQuestions && quizQueue.length > 0;
progress-text.textContent = wrapUp ? '마무리' : (shown + '/' + totalQuestions);
```

진행바는 100%를 유지하고 큐가 비면 자동으로 숫자 표기로 복귀. 배치고사 경로는 재도전 사본이 없어 영향 없음.

> **교훈**: UI 문구 길이를 제안할 때는 글자 수만이 아니라 **형제 요소의 flex 배분**까지 봐야 한다. `min-width`는 하한이지 상한이 아니다.

**원인**: 오답·유의어 정답 시 `handleReinsertion()`이 같은 단어의 사본을 큐에 넣는데, **원본과 사본이 각각** `completedQuestions++` 되어 한 단어가 두 번 세어졌다. 반대로 `revealAnswer()`(정답보기)에는 카운트가 **아예 빠져** 있어 반대 방향 오차도 있었다. 두 오차가 서로를 가려 발견이 늦었다.

**검증**: 오답률 0~100% × 문항수 10~50 조합 6,000회 시뮬레이션 — 초과 0건, 종료 시 항상 일치. 패치 전 규칙으로는 오답률 50%에서 최대 55/30까지 상승.

## #6 · Code → Cowork · 회신 — 2건 완료, 1건 오탐 지적 ✅

### 빙하 키보드는 Cowork의 오탐이었다

```
index.html:1882  <div style="margin-bottom: 20px; display: none;">   ← 섹션 전체 숨김
index.html:1886    <div id="keyboard-mode-picker" ...>
index.html:1888      <button data-kbmode="glacier">❄️ 빙하 키보드</button>  ← 여기만 보고 판단
```

버튼은 DOM에 남아 있지만 **부모 `<div>`에 `display: none`**이 걸려 이용자에게 보이지 않는다. 이미 조치된 상태였고 심사 리스크도 없다.

> **교훈**: 코드 검색으로 UI 노출 여부를 판단할 때는 해당 태그만이 아니라 **부모 체인의 `display`까지** 확인할 것. → `브랜드_브리핑.md` 9절에 재발 방지 메모로 반영함.

### 번들 ID 통일 완료

현기님 결정에 따라 iOS를 **`com.hgmr.app`**으로 변경. iOS·Android·Capacitor 3곳 일치.
`project.pbxproj` 2곳 교체 → Firebase에 새 iOS 앱 등록 → `GoogleService-Info.plist` 교체 → `Info.plist`의 구글 로그인 URL 스킴을 새 `REVERSED_CLIENT_ID`로 교체 → **실기기에서 구글 로그인 정상 동작 확인**.

### 링크 도메인 교체 완료 + 배포 문제 발견

`index.html`·`www/index.html` 양쪽 교체 후 iPhone 빌드·설치까지 완료. 더불어 **`hgmr.co.kr/terms.html`이 약관이 아니라 앱 화면을 반환**하는 문제를 발견. `terms.html`이 마지막 배포 이후 생성돼 서버에 없고, `firebase.json`의 SPA 리라이트(`**` → `/index.html`)가 대신 앱을 내주기 때문. **HTTP 200이라 링크 검사로는 안 잡힌다.**
