## 0. ⚠️ 2026-08-01 확인 — **기능은 전부 겹칩니다. 값은 「설명의 품질」에 있습니다**

현기님이 촬영한 말해보카 실제 화면 10장에서 확인했습니다 (`docs/경쟁분석_말해보카.md` v4).

### 겹치는 것 — 이 문서가 설계하려던 것 전부

| 우리 설계 | 말해보카 |
|---|---|
| 3단 판정 (정답 / 아깝다 / 오답) | 🔍 **말풍선 3색** — 초록·분홍·보라 |
| 유의어인데 더 맞는 답이 있음 → 재도전 | 🔍 *"clearly도 정답인데, 다르게도 표현할 수 있어요. 맞혀 보시겠어요?"* |
| **근접 오답의 뜻을 풀어주고 왜 아닌지 설명** | 🔍 *"put ~ away는 다 쓴 물건을 '치운다'는 거예요. '제쳐놓다'는 뭐라고 할까요?"* |
| 정답을 보여주지 않고 그 자리에서 재도전 | 🔍 동일 |

**기능 수준에서 겹침이 사실상 100%입니다.** 만들지 말자는 게 아니라, **홍보에서 고유 기능처럼 내세우면 안 된다**는 뜻입니다(원칙 P48).

> 참고로 v3 단계(화면 5장)에서 저는 *"그들은 왜인지 설명하지 않는다"*고 썼는데 **틀렸습니다.** 초록 말풍선 하나만 보고 단정했고, 추가 5장에서 분홍 말풍선이라는 반례가 나왔습니다.

### 그래서 남는 것 — **해상도**

`put away`와 `set aside`의 차이는 **영어를 모르는 사람에게 주는 뜻풀이**입니다.
`감소 / 절감 / 축소`의 차이는 **셋 다 아는 사람에게만 성립하는 대조**입니다.

같은 기능이라도 **모어 화자를 상대할 때만 닿는 깊이**가 있습니다. 이 문서의 값은 여기에만 있습니다.

**단, 이건 아직 가설입니다.** 근거는 *"외국어 학습자에게는 그 대조를 받아들일 바탕이 없다"*는 상식이지 관찰이 아닙니다. **1,043건의 주석이 실제로 그 깊이에 도달해야만 참이 됩니다.** 설명이 사전 뜻풀이 수준이면 그들과 똑같아집니다.

> **결론: 이 문서에서 가장 중요한 절은 3절(데이터 모델)도 4절(UX)도 아니고, 6절(어떤 쌍부터 주석하나)과 「설명을 어떻게 쓰는가」입니다.** 차별점이 기능이 아니라 글쓰기에 달렸기 때문입니다.
>
> 좋은 소식이기도 합니다 — 기능은 복제되지만 좋은 설명 1,043개는 복제하기 번거롭습니다. **자원이 적은 쪽이 이길 수 있는 유일한 종류의 싸움입니다.**

## 0-1. ⚠️ 2026-08-02 방향 수정 — **설명문이 아니라 「대조 예문」**

말해보카도 뉘앙스를 설명합니다(0절). 그래서 **설명문으로는 형식이 겹칩니다** — 말풍선에 사전 뜻풀이 한 줄을 띄우는 것까지 똑같아집니다.

`docs/표층_차별화_지침.md` 4-2절의 결론을 여기 반영합니다.

### 바뀌는 것

| | 기존 설계 | **수정** |
|---|---|---|
| `nuance` 값 | **설명문** — *"「망명」은 정치적 보호를 구해 나라를 옮기는 것. 여기선 처벌을 피해 숨은 것이라 「도피」가 맞아요."* | **대조 예문** — *"그는 정치적 박해를 피해 프랑스로 ____했다."* |
| 화면 | 말풍선에 설명 표시 | **문장이 잠깐 교체됐다 돌아옴** |
| 말 | 있음 | **없음 — 보여주기만 함** |

```
1.  빈칸에 「망명」이 들어가 문장이 완성된다        (0.6초)
2.  문장이 교체된다
        그는 정치적 박해를 피해 프랑스로 [망명]했다.
3.  원래 문장으로 돌아오고 빈칸이 비워진다
```

### 왜 이 편이 나은가

1. **형식이 다릅니다.** 글자를 다 지워도 다른 화면입니다 — 한쪽은 말풍선이 하나 늘고, 한쪽은 문장이 바뀌었다 돌아옵니다
2. **쓰기 쉽습니다.** 1,043번의 판단이 *"설명을 짓는 일"*에서 *"예문을 고르는 일"*로 바뀝니다
3. **품질 편차가 작습니다.** 설명은 잘 쓰고 못 쓰고가 갈리지만, **예문은 맞고 틀리고**입니다. 1,043건을 혼자 쓰는 상황에서 이 차이는 큽니다
4. **기존 자산을 재활용합니다.** 「망명」이 target인 문항이 이미 있으면 그 예문을 그대로 씁니다
5. **P38과 같은 축입니다** — *예문은 그 단어가 유일하게 잘 맞는 문장이어야 한다*. 문항 기준이 곧 뉘앙스 기능이 됩니다

### 데이터 모델에 미치는 영향

3절의 구조는 그대로이고 **값의 성격만 바뀝니다.**

```json
{
  "target": "도피",
  "accepts": ["도피", "도주", "도망"],
  "nuance": {
    "망명": { "ref": "망명" },
    "탈출": { "s": "그는 무너지는 건물에서 가까스로 ____했다." }
  },
  "nuanceDone": true
}
```

- `ref` — **`words.json`에 그 단어가 target인 문항이 있으면 그 예문을 가리킵니다.** 값을 새로 쓸 필요가 없습니다
- `s` — 없을 때만 짧은 대조 예문을 직접 씁니다
- ⚠️ **`ref` 우선으로 채우면 작업량이 줄어듭니다.** 실측 결과는 바로 아래

### 📊 실측 — `ref` 커버리지 **25.0%**

바로 세어 봤습니다.

```
주석 대상 (문항, 유의어) 쌍 : 1,091
고유 단어쌍                 : 1,088
  그중 유의어가 표제어로 존재 : 272   (25.0%)   ← ref로 공짜
직접 써야 할 대조 예문       : 816 건
```

**기대보다 낮습니다.** 4분의 1만 공짜입니다.

그래도 의미가 큽니다.

- **272건이 작업량에서 빠집니다.** `{"ref": "절감"}` 한 줄이면 끝이고, 예문 품질은 이미 검수를 거쳤습니다
- **`감소 ← 절감`, `갈망 ← 열망`, `강구 ← 수립` 처럼 가장 헷갈리는 쌍들이 여기 들어 있습니다.** 6절 우선순위와 겹칠 가능성이 높으니, **`ref` 커버 쌍부터 착수**하면 초기 비용이 거의 0입니다
- 나머지 816건도 **설명문을 짓는 것보다 예문 한 줄을 쓰는 편이 빠릅니다**

> **6절 우선순위를 다시 짤 때 `ref` 여부를 첫 번째 정렬 키로 두세요.** 「출제 빈도 × ref 있음」 순으로 가면 들이는 노력 대비 체감이 가장 큽니다.

### 설명문이 아예 사라지는 것은 아닙니다

예문만으로 차이가 안 드러나는 쌍이 있습니다(추상 명사끼리, 예: `절감`/`축소`). 그때는 짧은 한 줄을 덧붙이되 **기본은 예문**입니다.

## 0-2. ⚠️ 2026-08-05 — **「유일하게」가 빠졌습니다** (P38 완화)

> 현기님: *"'유일하게' 잘 맞아야 하는 것은 아님. 말이 되는 단어는 여러 개 있을 수 있음."*

이 문서는 *"예문은 그 단어가 **유일하게** 잘 맞는 문장이어야 한다"*를 전제로 쓰였습니다. **그 전제가 완화됐습니다.**

| | 기존 | **수정** |
|---|---|---|
| `accepts` | 좁게 — 정말 바꿔 써도 되는 것만 | **넓게 인정해도 됨.** 지금 「유의어 재도전」으로 튕기는 것 중 상당수는 그냥 정답 처리 |
| `nuance`의 역할 | *"이건 **틀렸다**"* | ***"이것도 되는데 더 잘 맞는 게 있다"*** |
| 「아깝다」의 무게 | 오답에 가까움 | **정답에 가까움** — 되는데 더 나은 답이 있을 뿐 |

### 「대조 예문」 방식이 오히려 더 잘 맞습니다

0-1절에서 `nuance` 값을 **설명문에서 대조 예문으로** 바꾸기로 했는데, 이 완화와 정확히 붙습니다.

- 설명문은 *"「망명」은 …이라 여기선 「도피」가 맞아요"* — **틀렸다고 말하는 형식**입니다
- 대조 예문은 *"네 단어는 이 문장의 것"*을 보여주고 돌려보낼 뿐이라 **틀렸다고 말하지 않습니다**

**P38이 완화되지 않았다면 대조 예문 방식이 오히려 어색했을 것입니다.** 두 결정이 맞물려 방향이 하나로 정리됐습니다.

### 2절 「규모」 숫자를 다시 봐야 합니다

주석 대상 1,091쌍은 **「`accepts`에 있지만 정답은 아닌 것」** 기준으로 셌습니다. `accepts`를 넓게 인정하기로 했으므로 **상당수가 그냥 정답으로 빠집니다.**

→ **실제 주석 대상은 1,091건보다 적습니다.** 얼마나 적은지는 `accepts` 재분류를 해봐야 알 수 있고, 6절 우선순위를 짤 때 함께 하면 됩니다.

## 1. 무엇을 만드나

지금 `accepts`는 평평한 목록입니다. 유의어를 쓰면 "유의어네요"로 끝납니다.
이걸 **두 갈래로 나누고, 갈라지는 지점에서 이유를 알려주자**는 것입니다.

| 이용자 입력 | 지금 | 앞으로 |
|---|---|---|
| `도피` (정답) | 정답 | 정답 |
| `도주` (문맥상 바꿔 써도 무방) | 유의어 → 재도전 유도 | **정답 인정** — "이 문맥에선 둘 다 맞아요" |
| `망명` (말은 되지만 뜻이 다름) | 유의어 → 재도전 유도 | **아깝다** — *"「망명」은 정치적 보호를 구해 나라를 옮기는 것. 여기선 처벌을 피해 숨은 것이라 「도피」가 맞아요."* |

이게 이 앱이 사전이나 단순 암기 앱과 갈라지는 지점입니다. **"맞았다/틀렸다"가 아니라 "왜 이 단어인가"를 가르치게 됩니다.**

동시에 **문항 선정 기준**이 되기도 합니다 — 예문은 그 단어가 *유일하게 잘 맞는* 문장이어야 합니다.

## 2. 규모 — 먼저 재고 시작합니다

| 항목 | 값 |
|---|---|
| 전체 단어 | 1,390 |
| 유의어를 가진 단어 | 738 (53%) |
| 주석 대상 (문항, 유의어) 쌍 | **1,091** |
| 고유 단어쌍 | 1,043 |
| **쌍당 평균 재사용** | **1.05회** |

### ⚠️ 단어쌍 사전으로 묶는 접근은 값이 없습니다

처음엔 "`감소 ↔ 절감` 같은 대조를 한 번 써서 여러 문항에 재사용하자"고 생각했는데, **실측해 보니 재사용률이 1.05회**입니다. 2회 이상 겹치는 쌍은 47종뿐이고 95개 문항만 커버합니다.

즉 **1,043번의 개별 판단**이 필요합니다. 비용을 줄일 지렛대는 재사용이 아니라 **우선순위**입니다(6절).

## 3. 데이터 모델 — 기존 구조를 깨지 않는 쪽으로

### 제안: `accepts`는 그대로 두고 `nuance`를 더한다

```json
{
  "target": "도피",
  "accepts": ["도피", "도주", "도망"],
  "nuance": {
    "망명": "정치적 보호를 구해 나라를 옮기는 것. 여기선 처벌을 피해 숨은 것이라 「도피」가 맞아요.",
    "탈출": "갇힌 곳에서 빠져나오는 것. 여기선 나라를 떠나 숨은 것이라 「도피」가 더 정확해요."
  },
  "nuanceDone": true
}
```

**`accepts`의 의미를 바꾸지 않는 것이 핵심입니다.** 이걸 건드리면 다음이 전부 영향을 받습니다.

- `check_words.js` 품질 검사
- `sync_words.js` Firestore 동기화
- `admin.html` 검수 패널
- `word_stats` 집계 (유의어 배지 판정에 `accepts` 사용)
- **SwiftUI 프로토타입** (`swiftui-app/`) — 별도 구현체라 스키마가 바뀌면 같이 깨집니다

`nuance`는 선택 필드라 없으면 지금과 똑같이 동작합니다. **문항 단위로 하나씩 옮겨갈 수 있습니다.**

### `nuanceDone` 플래그가 필요한 이유

주석 전후로 `accepts`의 **판정 결과가 달라지기** 때문입니다.

| | `nuanceDone: false` (미주석) | `nuanceDone: true` (주석 완료) |
|---|---|---|
| `accepts` 안의 말 | 지금처럼 유의어 → 재도전 유도 | **정답 인정** (재도전 없음) |
| `nuance` 키 | — | **아깝다** → 설명 + 재도전 |

플래그가 없으면 "이 단어는 검토를 거쳐 accepts가 정제된 것인가, 아직 손 안 댄 것인가"를 구분할 수 없습니다. 미주석 문항은 **지금 동작을 그대로 유지**해야 안전합니다.

> 대안으로 "근접어를 accepts에서 빼고 nuance로 옮긴다"만 하는 방법도 있는데, 이러면 미주석 문항이 전부 관대해지는(재도전이 사라지는) 쪽으로 동작이 바뀝니다. **플래그 방식을 권합니다.**

## 4. 학습 경험 — **정답을 보여주지 않고 그 자리에서 다시 풀게 한다**

> 2026-07-30 개정 — 현기님 제안 반영. 처음 설계는 「정답 공개 + 설명 → 나중에 재도전」이었는데,
> **「설명만 하고 정답은 숨긴 채 제자리에서 재입력」**으로 바꿉니다.

### 왜 이쪽이 맞나

- **인출이 기억을 만듭니다.** 정답을 보여주면 그 순간 인출 기회가 사라집니다. 힌트를 받고 **스스로 떠올려 맞히는 것**이 훨씬 강하게 남습니다
- **맥락이 살아 있을 때 설명해야 합니다.** 3~6문제 뒤 재도전은 문장의 결이 이미 흐려진 뒤입니다
- 힌트가 이미 강합니다. "「망명」은 정치적 보호를 구하는 것"까지 들으면 목표어를 떠올릴 확률이 충분히 높습니다 — **성공적 인출**이 일어나기 좋은 난이도
- "정답입니다! 그런데 아쉽습니다" 같은 **엇갈린 메시지가 사라집니다**

### 구현 비용은 거의 없습니다 — 이 흐름이 이미 있습니다

`checkAnswer()`의 `_synRetry` 분기(`index.html:4665` 부근)가 **정확히 이 동작**입니다.

```js
if (currentWord._synRetry) {
    inputGroup.classList.add('synonym');   // 빨간 오답(.wrong)과 구분되는 상태
    inputEl.value = '';                    // 입력만 비우고
    inputEl.placeholder = '정답 입력';      // 정답은 보여주지 않음
    harangSay('좋은 단어예요! 아까 본 단어를 떠올려 볼까요?', 2800);
    isWaiting = false;
    return;                                // 큐를 넘기지 않고 제자리 대기
}
```

**말풍선 문구를 뉘앙스 설명으로 바꾸고, 이 분기를 근접어(`nuance`) 입력 시에도 타게 하면 됩니다.** `.synonym` 상태 스타일도 이미 있습니다(`index.html:886`). 정답 보기 버튼도 이 상태에서 살아 있어 막히면 빠져나갈 길이 있습니다.

### 판정 3단계

| 입력 | 화면 | 큐 |
|---|---|---|
| target | 정답 | 다음 문제 |
| `accepts` | ✅ 정답 — "이 문맥에선 「도주」도 맞아요" | 다음 문제 |
| `nuance` | 🦭 **설명만, 정답 미공개** | **제자리 재입력** |
| 그 외 | 오답 | 제자리 재입력 |

### ⚠️ 따라오는 결과 — 뉘앙스 문구에 정답을 쓸 수 없습니다

이게 이 변경의 가장 큰 파급입니다. 처음 설계의 문구는 이랬습니다.

> ~~「망명」은 정치적 보호를 구해 나라를 옮기는 것. 여기선 처벌을 피해 숨은 것이라 **「도피」**가 맞아요.~~

정답을 숨기기로 했으니 **목표어를 입에 담으면 안 됩니다.** 문구의 성격이 *판정문*에서 **변별 힌트**로 바뀝니다.

> 🦭 「망명」은 정치적 박해를 피해 **다른 나라의 보호를 받는 것**이에요.
> 이 사람은 보호를 구한 게 아니라, 처벌을 피해 **몸을 숨긴 거죠.**

작성 규칙이 이렇게 바뀝니다.

1. **목표어를 쓰지 않는다** — 쓰는 순간 답이 공개됩니다
2. **입력한 말의 뜻을 먼저 짚는다** — 왜 여기에 안 맞는지가 드러납니다
3. **이 문맥에서 필요한 뜻을 목표어 없이 서술한다** — 이게 곧 힌트입니다
4. **이미 화면에 있는 뜻풀이와 겹치지 않게 쓴다** — 뜻풀이는 이미 보이고 있습니다. 뉘앙스 문구는 **대조 정보**를 더해야 값이 있습니다
5. 60자 이내 · 설명은 담백한 존댓말, 하랑이 리액션만 반말

> 결과적으로 이 문구는 **"이 문장에서만 통하는 두 번째 뜻풀이"**가 됩니다. 쓰기는 조금 더 어렵지만 산출물의 값은 더 큽니다.

### 세부 규칙

- **힌트 상한 2회.** 근접어를 연달아 입력하면 두 번까지 설명하고, 그 뒤에는 일반 오답 흐름으로 넘깁니다. 무한 힌트 방지
- **정답 보기 버튼은 계속 열어 둡니다.** 막히면 나갈 수 있어야 합니다
- **`.wrong`(빨간 흔들림)을 쓰지 않습니다.** `.synonym` 상태로 "틀린 게 아니라 아까운 것"임을 시각적으로 구분
- **채점** — 지혜 조각은 지급, **첫 시도 정답 EXP(+20)는 제외**, **어휘 고도에는 오답으로 넣지 않습니다.** 뜻을 알고 근접한 답을 낸 것이라 실력 하향 신호가 아닙니다

### 세션 중 재출제 사본은 넣지 않습니다

지금은 유의어를 맞히면 3~6문제 뒤에 `_synRetry` 사본을 큐에 넣습니다. **근접어 경로에서는 이걸 빼는 쪽을 권합니다.**

- 제자리에서 이미 해결했으므로 중복입니다
- 간격 복습은 **SRS가 다음 날 이후로 이미 담당**합니다 (1·3·7·14·30일)
- 덤으로, 최근에 고친 「`30/30` 도달 후에도 문항이 남는 구간」이 이 경로에서는 아예 생기지 않습니다

## 5. 콘텐츠 선정 기준 — 앞으로 만들 문항에도 적용

현기님이 말씀하신 "예문에서 그 단어가 정말 잘 들어맞아야 한다"를 **작성 규칙**으로 못 박습니다.

새 문항을 만들거나 기존 문항을 검수할 때:

1. **유일성** — 이 빈칸에 target이 다른 어떤 유의어보다 잘 맞는가? 아니면 문장을 고친다
2. **변별 단서** — 문장 안에 target을 고르게 하는 단서(공기어·문맥)가 있는가? `제 ____을 다하다`(12자)처럼 단서가 없으면 무엇을 넣어도 맞다
3. **유의어 처리** — 떠오르는 유의어를 전부 적고, 각각 ① 여기서도 맞음 ② 말은 되지만 target이 나음 ③ 아예 틀림 으로 가른다
4. **②가 하나도 없으면 문항의 교육 가치가 낮다** — 가르칠 대조가 없다는 뜻

### 주석하다 보면 문항 결함이 드러납니다

실제 사례입니다.

> **감소** — `마케팅 비용의 ____에 힘입어 영업이익 1천706억 원 기록`
> accepts: 절감 · 축소 · 감축

이 문맥에서는 **「절감」이 「감소」보다 낫습니다.** 비용을 *아껴서* 이익이 난 것이니까요. `감소`는 저절로 줄어드는 것입니다.

**주석 파이프라인은 "이 문항은 target이 최선이 아님 → 문항 수정"이라는 결론을 낼 수 있어야 합니다.** 이 판정이 나오면 레벨·태그가 아니라 문항 자체를 고쳐야 합니다.

## 6. 작업 순서 — 1,043개를 한 번에 하지 않습니다

재사용이 없으니 비용을 줄일 방법은 **안 해도 되는 것을 안 하는 것**뿐입니다.

### 1단계 · 실측으로 우선순위를 정한다 (선행)

`word_stats.answers`에는 **이용자가 실제로 입력한 답**이 전부 들어 있습니다. 여기서

- 각 문항별로 `accepts`에 속하면서 **실제로 자주 입력된** 유의어를 뽑는다
- 아무도 입력한 적 없는 유의어는 **주석 우선순위가 낮다** — 화면에 뜰 일이 없으니까

> 1,043개 전부가 아니라 **실제로 마주치는 것부터**. 응답이 쌓일수록 목록이 정확해집니다.
> 이 추출은 Code 쪽에서 뽑아 주시면 됩니다.

### 2단계 · 값싼 판정과 비싼 판정을 나눈다

| 판정 | 산출물 | 비용 |
|---|---|---|
| ① 여기서도 맞음 | `accepts` 유지, 텍스트 **없음** | 낮음 |
| ② 말은 되지만 target이 나음 | `nuance`에 **한 줄 작성** | 높음 |
| ③ 아예 틀림 | `accepts`에서 **제거** | 낮음 |
| ④ target이 최선이 아님 | **문항 수정 대상**으로 표시 | 별도 |

**텍스트를 써야 하는 건 ②뿐입니다.** ①·③은 분류만 하면 됩니다.

### 3단계 · 초안 생성 → 검수

- Cowork가 문항·뜻풀이·예문을 보고 **①②③④ 분류 + ②의 뉘앙스 문구 초안**을 만든다 (한 세션에 100~150개 규모)
- `admin.html`에 **뉘앙스 검수 화면**을 붙여 현기님이 승인·수정 (Code 작업)
- 승인분만 `words.json`에 반영, `nuanceDone: true`

### 4단계 · 측정

- `nuance_shown` 이벤트 (어느 문항의 어느 입력에서 떴는지)
- 뉘앙스를 본 뒤 재도전 문항의 정답률
- 그 단어의 **다음 SRS 회차 정답률** — 이게 진짜 지표입니다. 뉘앙스 설명이 기억에 남았는가

## 7. 단계별 릴리스

| 단계 | 범위 | 전제 |
|---|---|---|
| **0** | 스키마 필드만 추가 (`nuance`·`nuanceDone`), 동작 변화 없음 | — |
| **1** | 판정 3단계 + 화면 구현. 주석된 문항에서만 발동 | 0 완료 |
| **2** | 실측 상위 100~200개 주석 | 출시 후 응답 축적 |
| **3** | 검수 도구 + 지속 주석 | 1·2 완료 |

**0·1은 데이터 없이도 지금 할 수 있습니다.** 2는 실사용 데이터가 있어야 우선순위가 나옵니다.

## 8. 언제 착수할지 — 제 의견

**출시 이후를 권합니다.**

- 지금 App Store 제출을 막는 것은 연령 등급 설문과 스크린샷뿐입니다. 이 기능은 출시를 앞당기지 않습니다
- 2단계(주석)의 우선순위는 **실사용 데이터가 있어야** 정해집니다. 지금 하면 아무도 입력하지 않을 유의어에 시간을 씁니다
- 다만 **5절의 문항 선정 기준은 지금부터 적용**하는 게 좋습니다. 앞으로 만드는 문항이 이 기준을 통과하면 나중에 주석할 일이 줄어듭니다

순서를 제안하면: **출시 → 데이터 2~4주 축적 → 0·1단계 구현 → 실측 상위부터 주석**.
