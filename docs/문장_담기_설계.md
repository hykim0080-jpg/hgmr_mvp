# 「문장 담기」 — 공유 시트로 받는 개인 문장 수집

> 작성: Cowork · 2026-07-30 · 구현: Code
> 상태: **설계 제안** — 착수 전 검토 필요

---

## 1. 한 줄

**일상에서 만난 문장을 공유 시트로 한글마루에 보내면, 내가 배운 단어를 짚어주고 모르는 단어는 담아 둔다.**

---

## 2. 왜 이게 값이 있나

### 구조적 비대칭

한국에서 영어를 배우는 사람은 일상에서 영어 문장을 마주칠 일이 드뭅니다. **한국어 사용자는 온종일 한국어에 둘러싸여 있습니다.**

같은 기능을 영어 앱이 붙여도 쓸 일이 없고, 국어 앱에서는 매일 쓸 수 있습니다. **기능이 아니라 대상이 만드는 차이**라 따라 해도 소용이 없습니다.

### OCR을 만들지 않아도 됩니다

사진 속 문장도 커버됩니다 — **OS가 이미 해주기 때문입니다.**

- iOS **라이브 텍스트**: 사진 속 글자 길게 누르기 → 선택 → 공유
- 안드로이드 **구글 렌즈 / 갤러리 텍스트 인식**: 동일

**우리는 텍스트만 받으면 됩니다.** 카메라 권한 불필요, OCR 라이브러리 불필요, 이미지 저장·용량 문제 없음. 사진·웹·메신저·전자책·PDF가 전부 하나의 입구로 들어옵니다.

### 콘텐츠 병목에 숨통

단어 1,390개는 헤비 유저가 몇 주면 소진합니다. 사용자가 가져오는 문장은 **고갈되지 않는 재료**입니다.

---

## 3. 받은 다음에 무엇을 하나 — 여기가 성패입니다

**그냥 저장만 하면 실패합니다.** 포켓·에버노트가 다 겪은 문제 — 저장은 하는데 다시 안 봅니다. *"수집했다는 만족"이 "학습"을 대체*해 버립니다.

받은 문장을 **즉시 학습 루프에 연결**해야 합니다.

### 받는 즉시 보여줄 것

```
받은 문장:
"이상으로 꿈꾸는 자아와 현실의 나 사이의 괴리 탓에 우리는 스스로를 자책하게 된다."

✅ 배운 단어 2개    괴리 · 자책
＋ 담을 만한 단어    이상 · 현실
```

1. **내가 배운 단어를 하이라이트** — *"배운 게 실제 글에 나온다"*는 확인. 이게 이 기능의 감정적 핵심입니다
2. **아직 안 배운 단어는 탭해서 담기** — 개인 단어장으로
3. 담긴 단어는 **다음 세션에 우선 출제**

3번이 결정적입니다. **스크랩이 스크랩으로 끝나지 않게 하는 유일한 장치**입니다.

---

## 4. 범위 — 처음엔 좁게

### 넣을 것

- 텍스트 수신 (공유 시트)
- 문장 저장 · 목록 보기 (「내 문장」)
- 어휘 사전과 매칭해 **배운 단어 하이라이트**
- 안 배운 단어 **담기** → 다음 세션 우선 출제

### 처음엔 넣지 않을 것

| 제외 | 이유 |
|---|---|
| **받은 문장을 문항으로 자동 변환** | *"예문에서 그 단어가 유일하게 잘 맞아야 한다"*는 문항 기준(`docs/유의어_뉘앙스_설계.md` 5절)을 자동 생성이 만족시키기 어렵습니다. 품질이 무너집니다 |
| **다른 사용자와 공유** | 저작권 안전선입니다. 아래 6절 |
| 사진 자체 저장 | OS가 OCR을 해주므로 불필요. 용량·권한만 늘어납니다 |
| 태그·폴더·검색 | 문장이 수십 개 쌓이기 전엔 필요 없습니다 |

---

## 5. 플랫폼별 비용 — **순서가 중요합니다**

| 플랫폼 | 방법 | 비용 |
|---|---|---|
| **웹 (PWA)** | `manifest.json`에 `share_target` 선언 | **매우 낮음** — 설정 몇 줄 |
| **안드로이드** | `AndroidManifest.xml`에 `ACTION_SEND` / `text/plain` intent-filter | 낮음 |
| **iOS** | **Share Extension 별도 타깃** + App Group으로 데이터 전달 | **높음** — Capacitor 웹뷰 밖의 네이티브 작업 |

### 제안 순서

**웹 → 안드로이드 → iOS**

iOS Share Extension은 별도 익스텐션 타깃을 만들고 App Group으로 본체와 데이터를 주고받아야 해서, 지금까지의 Capacitor 작업과 성격이 다릅니다. **가장 비싼 걸 먼저 만들지 않는 편이 좋습니다.**

웹은 거의 무료로 붙일 수 있어 **가설 검증용**으로 적합합니다. 사람들이 실제로 문장을 보내는지 먼저 보고, 쓰인다면 iOS에 투자하는 순서를 권합니다.

> 다만 주 타깃이 iOS라면 웹 검증의 표본이 편향될 수 있습니다. 이건 감안하셔야 합니다.

---

## 6. 저작권 — 안전선 하나만 지키면 됩니다

**받은 문장을 다른 사용자에게 노출하지 않는 것.**

- 개인이 읽은 글을 자기 계정에 저장하는 건 **사적 이용**의 범위입니다
- 그걸 앱 콘텐츠로 돌리거나 다른 사용자와 공유하는 순간 성격이 달라집니다
- Firestore `users/{uid}` 하위에만 저장하고, `word_stats` 같은 전역 컬렉션에 넣지 않으면 됩니다
- 통계로 쓰더라도 **문장이 아니라 단어 단위 집계**만 (예: "이 단어를 담은 사람 수")

지금 예문 출처 문제가 이미 있는 상황이라 이 선은 명확히 그어두는 게 좋습니다.

---

## 7. 계측

| 이벤트 | 파라미터 | 보는 것 |
|---|---|---|
| `share_received` | `source`(web/android/ios), `length` | 실제로 쓰이는가 |
| `sentence_saved` | `known_words`, `new_words` | 문장 하나당 수확량 |
| `word_added_from_sentence` | `word` | 어떤 단어를 담는가 → **콘텐츠 확장 힌트** |
| `saved_word_quizzed` | `correct` | **담은 단어를 실제로 학습하는가** |

마지막 지표가 핵심입니다. **담기만 하고 안 푼다면 이 기능은 스크랩북일 뿐입니다.**

`word_added_from_sentence`는 부수적으로 값집니다 — **사용자가 담는 단어가 곧 words.json에 없는 단어 목록**입니다. 다음에 무엇을 추가할지 알려주는 신호입니다.

---

## 8. 열어둔 질문

1. **로그인 없이도 쓸 수 있게 할 것인가?** 익명 이용자도 문장을 담을 수 있어야 하는지. 담을 수 있게 하면 진입이 쉽지만 기기 교체 시 사라집니다
2. **문장 길이 상한?** 기사 전문을 통째로 보내는 경우가 있습니다. 300자쯤에서 자르거나 첫 문단만 받는 편이 나을 듯합니다
3. **「내 문장」을 어디에 둘 것인가?** 낱말카드 옆? 홈의 새 카드? 화면 하나가 늘어나는 문제입니다
4. **웹 검증을 건너뛰고 바로 iOS로 갈 것인가?** 주 타깃이 iOS라 표본 편향이 있습니다. 비용과 정확도의 맞교환입니다

---

## 9. 언제

**출시 이후입니다.** 지금 App Store 제출을 막는 건 연령 등급 설문과 스크린샷뿐이고, 이 기능은 출시를 앞당기지 않습니다.

다만 **웹 `share_target`은 예외로 볼 만합니다.** `manifest.json` 몇 줄이라 출시 전에 넣어도 위험이 거의 없고, 웹 이용자에게 먼저 반응을 볼 수 있습니다.
